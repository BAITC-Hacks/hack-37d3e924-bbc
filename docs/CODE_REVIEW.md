# Ревью команды — 23.09.2026

Объект проверки: код текущей ветки `main`, независимый проход по 52 файлам кода, контрактов, тестов и документации, плюс наличие приложения в `backend/` и `frontend/`. Исправления проверены синтетическими регрессиями. Реальные записи, транскрипты и документы совещаний в рамках ревью не открывались и не передавались внешним API. Модели и контракт результата не заменялись.

## Вывод

Текущие исправления приняты после независимого повторного ревью. Полный согласованный P0: **REQUEST CHANGES / архитектурный BLOCK**. Репозиторий содержит отдельные работающие компоненты, но общий сценарий FastAPI/React/SQLite → `ai.pipeline.run_pipeline` отсутствует. Локальный прототип: **WATCH**, с перечисленными ниже исправлениями и ограничениями среды. Успешные unit-тесты не означают успешное распознавание или извлечение поручений.

## Оставшиеся блокеры и поручения

| Приоритет / владелец | Следующий результат | Критерий готовности / зависимость |
|---|---|---|
| P0 / участник 2 | Один согласованный путь приложения к `run_pipeline`, сохранение оригинала и правок, экспорт | Загрузка → реальный worker → результат по `contracts/` → правка → повторное открытие → DOCX; зависит от работающего профиля участника 1. Текущий прототип не реализует обещанный REST API и SQLite |
| P0 / участник 1 | Подготовить исходные веса и поддержанную среду без замены модели | Проверка SHA-256 исходного ASR, работоспособность исходного MLX LLM; воспроизводимый полный прогон. На текущей Windows-машине ASR отсутствует, MLX runtime недоступен |
| P0 / оба участника | Ранний реальный сквозной запуск на одной машине | Один worker, доступный ему путь аудио, сохранение источников поручений, корректные ошибки; не запускать два независимых конвейера на одном ограниченном GPU одновременно |
| P1 / участник 1 + тимлид | Приёмка RU/KZ/mixed и измерения | Три записи из плана приёмки, минимум два голоса; время, память, ошибки, исполнитель отличается от говорящего, отсутствующий срок, относительная дата, не-поручение |
| P1 / участник 2 + тимлид | Проверить итоговый DOCX и повторный запуск | Визуально проверить страницы, таблицы и казахские буквы после правок; запуск другим человеком по README; полный прогон без исходящего доступа после подготовки зависимостей |
| P1 / тимлид | Зафиксировать единую точку интеграции и доказательства готовности | Обе стороны используют одну принятую схему; статус `FROZEN` не объявляется без фактического согласия; в защите отдельно назвать подтверждённое и незавершённое |

Это распределение по зоне ответственности, а не установление авторства каждого дефекта. По одному состоянию репозитория нельзя оценить вклад человека, доступные ему ресурсы и качество договорённостей. Оснований рекомендовать увольнение по этому ревью нет. Приёмка должна опираться на воспроизводимый результат каждой зоны.

## Доказательства и границы проверки

- Windows 11, Python 3.14.6, подготовленная `.venv` прототипа.
- Общий pytest: **98 PASS за 16,67 с**, без переменной `PYTHONUTF8`, после исправлений интерфейса, экспорта и Windows-совместимости: 50 AI + 48 прототипа.
- `contracts/verify.ps1`: PASS, включая отклонение шести некорректных вариантов.
- `compileall` изменённых Python-модулей и AI: PASS; `git diff --check`: PASS.
- Текущий локальный сервер: `GET /_stcore/health` → `ok`.
- Три исходные UI-ошибки сначала воспроизведены падающими регрессионными тестами, затем эти же тесты прошли с исправлениями.
- Сохранность DOCX проверена программно на синтетическом документе; новая визуальная проверка рендера страниц не выполнялась.
- Пустой список поручений проверен через UI. Валидация ручных источников покрыта тестами; добавление новой строки кликами в `st.data_editor` отдельно не автоматизировано: установленный AppTest предоставляет его как `Dataframe`.
- Полный inference, GPU-конфигурация, актуальные тарифы, точность моделей и запрет сети на уровне ОС в этом ревью не проверялись. Данные предыдущего частичного smoke в `data/` не засчитываются как полный E2E.
